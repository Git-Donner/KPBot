# KPBot P0 性能结果统计分析改动报告

## 1. 改动概述

本次改动针对 `code-optimizer` 插件中的 `vector-experiment-methodology` 技能，补齐向量检索性能对照结果的描述性统计，并完善对应的测量契约和测试。

改动的核心是：在已有中位数、加速比和样本数之外，为 baseline 与 candidate 分别输出 min、max、MAD 和小样本标记，使报告能够同时呈现性能水平与测量波动。

本次没有新增独立 SKILL、第三方依赖或可视化功能，也没有调整优化接受门槛。统计结果仍由现有验证和审核流程结合实验条件、正确性及业务目标进行判断。

所有交付文件均位于 `D:\workspace\KPBot\KPBot-zl`，保持原项目相对目录结构。`KPBot-zl` 是本次改动文件集合，不是完整项目副本；实施过程中未向 `KPBot-master` 写入修改。

## 2. 被修改模块的定位

### 2.1 所属插件与技能

所属插件：`Plugins/code-optimizer`。

所属技能：`vector-experiment-methodology`，即“向量检索实验方法”。

该技能定义向量检索性能对照的方法，包括冻结实验条件、交错运行 baseline 与 candidate、检查正确性、处理测量噪声，以及汇总实验结果。它是性能验证的支撑能力，不负责生成优化代码。

### 2.2 统计脚本的职责

技能中的 `scripts/compare_results.py` 读取约定格式的 JSON，按数据集比较 baseline 与 candidate。原版已具备以下功能：

- 校验性能字段及样本格式，拒绝缺失值、布尔值和非有限数值。
- 计算两侧性能中位数和样本数。
- 根据指标方向计算加速比及其百分比增幅。
- 汇总跨数据集的加速比几何平均。
- 报告正确性指标的中位数差异；数据不完整时标记不可用。
- 通过命令行输出 JSON，或者将结果写入指定文件。

本次在这些能力之上补充离散度统计，保留既有主要输出字段和计算口径。

## 3. 原版本存在的问题与改动必要性

### 3.1 测量契约与脚本实现不一致

原版 `references/measurement-contract.md` 要求：至少三个样本时报告 min/max 或 MAD。

但原版脚本主要输出中位数、加速比及样本数，没有实现对应的离散度字段。因此，直接使用脚本生成的摘要无法完整满足技能自己的统计报告约定，需要 Agent 或使用者额外计算。

补齐这项能力可以减少重复计算和报告遗漏，是本次改动最直接、最充分的依据。

### 3.2 中位数不足以表达测量波动

两组样本即使中位数相同，也可能具有不同的波动情况。只查看中位数和加速比，容易遗漏极慢轮次或运行条件不稳定的迹象。

新增 min/max 用于显示观测范围，MAD 用于表达围绕中位数的典型偏离程度。它们共同提供描述性证据，但不能单独证明优化收益具有统计显著性。

### 3.3 小样本结果缺少明确提示

原脚本允许单次测量参与对比。单次测量能够计算比值，但不能据此了解重复运行的波动情况。

新增小样本标记后，下游报告能够直接识别不足三次的测量。三次沿用原契约中的最低报告数量约定，不代表达到三次就具备充分统计证据。

### 3.4 非正数样本可能被正的中位数掩盖

原脚本检查性能中位数是否为正，但没有逐条拒绝零值和负值。例如 `[-1, 10, 20]` 的中位数为 10，原实现仍可能继续计算加速比。

对于本脚本所比较的正值吞吐、耗时指标，零值和负值可能来自失败占位、采集错误或不合适的输入口径。逐样本检查能够避免这些数据进入正常结果摘要。

这项修改收紧了输入约束。如果实际测试使用零值表达计时精度以下的耗时，接入方需要明确处理规则，不能直接沿用此前行为。

### 3.5 改善百分比存在误读空间

原脚本的 `improvement_percent` 来自加速比，而不是所有指标原值的下降比例。对于延迟指标，两者不同。

本次通过文档澄清其含义，避免报告中把“加速比增幅”写成“延迟下降比例”，没有改变原计算公式。

## 5. 具体实现

### 5.1 新增 baseline 与 candidate 统计字段

每个数据集的结果新增：

- `baseline_statistics`：baseline 的描述性统计。
- `candidate_statistics`：candidate 的描述性统计。

两者均包含以下字段：

| 字段 | 含义 |
| --- | --- |
| `min` | 全部有效性能样本中的最小值 |
| `max` | 全部有效性能样本中的最大值 |
| `mad` | 未乘缩放系数的绝对中位差，与输入性能指标同单位 |
| `sample_count_below_three` | 当前一侧样本数是否少于三次 |

原有 `baseline_median`、`candidate_median`、`speedup`、`improvement_percent`、两侧样本数和正确性字段保留。

### 5.2 MAD 的计算口径

计算公式：

```text
MAD = median(abs(x - median(x)))
```

以合成样本 `10、12、14、16、1000` 为例：

```text
中位数：14
绝对偏差：4、2、0、2、986
MAD：2
min：10
max：1000
```

该示例仅说明计算，不代表真实机器测试结果。

MAD 对极端值相对不敏感，因此不能单独用于判断是否存在慢轮次。本次同时输出 min/max，并且不根据 MAD 删除任何样本。

### 5.3 小样本处理

单样本和双样本仍输出描述性统计，并设置 `sample_count_below_three=true`。三次及以上设置为 `false`。

需要注意：

- 单样本的 MAD 为 0，只是该公式的计算结果。
- 多个相同样本的 MAD 也可能为 0。
- MAD 为 0 不代表环境稳定或收益显著。
- 标记为 `false` 只说明样本数量不少于三次，不代表统计证据充分。
- 两侧样本数可以不同，脚本不假设它们按位置配对。

### 5.4 数据校验

将原有数值读取逻辑提取为 `numeric_values()`，供中位数计算和描述性统计共用。性能样本在原有有限数值检查基础上增加正数检查。

如果任意性能样本小于或等于零，比较失败并报告错误，不会静默丢弃该样本后继续计算。

正数约束只针对性能字段。正确性字段仍沿用原规则，例如 recall 为零不会因此被拒绝。

本次没有加入自动清洗、异常值剔除、失败轮分类或数据插补。

### 5.5 百分比口径

保留原公式：

```text
吞吐越高越好：speedup = candidate / baseline
延迟越低越好：speedup = baseline / candidate
improvement_percent = (speedup - 1) * 100
```

例如延迟从 100ms 降至 80ms：

| 口径 | 结果 |
| --- | --- |
| 加速比 | 1.25 倍 |
| `improvement_percent`，即加速比增幅 | 25% |
| 延迟下降比例 | 20% |

文档明确二者不能混称；本次没有新增延迟下降比例字段。

## 6. 输出示例

以下为单数据集结果中的局部示例，使用合成输入：baseline 为 `10、12、14、16、1000`，candidate 为 `20、24、28、32、2000`。

```json
{
  "baseline_median": 14.0,
  "candidate_median": 28.0,
  "speedup": 2.0,
  "improvement_percent": 100.0,
  "baseline_samples": 5,
  "candidate_samples": 5,
  "baseline_statistics": {
    "min": 10.0,
    "max": 1000.0,
    "mad": 2.0,
    "sample_count_below_three": false
  },
  "candidate_statistics": {
    "min": 20.0,
    "max": 2000.0,
    "mad": 4.0,
    "sample_count_below_three": false
  }
}
```

示例中的两倍加速比只是样本中位数之比，不能据此认定真实优化已通过验收。

## 7. 兼容性与使用边界

### 7.1 保留的行为

- 命令行参数和输入主体结构保持不变。
- 性能指标方向仍由原有 `higher_is_better` 配置控制。
- 原有中位数、加速比、几何平均和百分比算法保持不变。
- 不完整正确性数据仍标记为不可用。
- 不新增第三方依赖。

### 7.2 需要注意的行为变化

第一，输出新增两个对象。按字段读取结果的调用方通常可以继续使用；如果下游严格禁止额外字段，需要同步调整对应约束。因此，不能宣称对所有消费者完全兼容。

第二，输入校验更加严格。此前可能被正中位数掩盖的零值、负值性能样本，现在会导致比较失败。使用失败占位值或零耗时的调用方应在接入前核实数据含义。

### 7.3 尚未实现的能力

本次范围限于现有向量检索比较脚本的统计补全，未实现：

- 置信区间、假设检验或自动显著性判断。
- 环境漂移检测和自动优化接受决策。
- 跨场景通用指标单位管理。
- app-tuner 的显式指标方向配置。
- 失败轮分类、自动重测和异常值清洗。
- 可视化图表、HTML 报告或历史回归看板。

这些能力需要独立的数据契约、调用场景和验证依据，未纳入本次小范围补充。

该改动处理已有测量结果，不改变被测业务代码，因此测试通过说明计算行为符合本次约定，不代表任何业务性能提升或实机优化验收通过。

## 9. 提交审核时的价值与注意事项

本次最适合强调的贡献是“落实已有测量契约”，而不是宣称新增完整性能分析平台。

主要价值包括：

1. 消除契约与脚本之间的缺口，使统计摘要直接满足离散度报告要求。
2. 增加测量波动和小样本信息，改善报告的可解释性。
3. 防止无效非正数性能样本被中位数掩盖。
4. 澄清百分比语义，减少优化报告误读。
5. 改动集中在单个技能及其测试中，无新增依赖，便于审核。

审核时应重点确认非正数性能样本的处理是否符合现有 benchmark 数据约定，以及是否存在严格限制额外输出字段的下游消费者。

本次没有必要为上述功能新建独立 SKILL。它们属于现有 `vector-experiment-methodology` 的职责范围，直接补齐原技能可以减少能力重复与后续维护成本。
